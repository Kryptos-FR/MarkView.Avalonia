# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MarkView.Avalonia is a Markdig-powered markdown viewer control for Avalonia UI v12. This file holds the rules for working in the repository; what the library does and how to use it is in the documentation below, which this file does not repeat.

## Documentation

`docs/` is the source of the documentation site, https://kryptos-fr.github.io/MarkView.Avalonia/, and is licensed under CC BY-SA 4.0 (`docs/LICENSE.txt`; its code samples are also MIT, like the code). Look there before reading the code to learn what a feature does:

| Path | Holds |
|---|---|
| `docs/getting-started.md`, `docs/packages.md`, `docs/upgrading.md` | Install and first document; which package adds what and its theme file; breaking changes since the last release |
| `docs/guides/` | One page per feature (displaying documents, Markdown and the pipeline, chat, streaming, code blocks, images and diagrams, math, themes, selection, find, folding, task lists, accessibility, right-to-left, custom extensions) |
| `docs/reference/` | Exhaustive tables: `MarkdownViewer` members, Markdown syntax, style classes, resource keys, theme preset values, versioning |
| `README.md`, `src/*/README.md` | Short landing pages (the root one is also the core package's NuGet page, and the demo's README tab); they link to the site with absolute URLs, since relative links break on NuGet |

- When a change alters public behaviour, update its guide, the matching reference table, and `docs/upgrading.md` if it breaks code written for the last release (check against its tag; a feature not released yet is never a breaking change).
- A feature's how-to goes in its guide under `docs/guides/` (short answer and example first, then details); exhaustive tables go under `docs/reference/`, and the guide links to them. Every page needs `title` front matter and an entry in the `menu.yml` of its folder.
- Link to other pages with relative `.md` links, and to repository files outside `docs/` with absolute GitHub URLs (a `../` link out of `docs/` breaks the build).
- The site is built with Lunet (`docs/config.scriban`, navigation in `docs/menu.yml`, API reference generated from the `src/` projects) and deployed with the browser demo under `/demo/` by `.github/workflows/site.yml`. It shows the latest release, not `main`: it deploys on each published release, on each push to a `docs/<version>` branch (cut from the release tag; documentation fixes merged to `main` are cherry-picked onto it), and on a manual run. Build locally with `dotnet tool install -g lunet` then `lunet build` in `docs/` (output in `docs/.lunet/build/www`).

## Build and test

```bash
dotnet restore --locked-mode        # CI uses locked NuGet lock files — regenerate with `dotnet restore --force-evaluate` if a PackageVersion changes
dotnet build
dotnet test                                                                              # run all tests (headless Avalonia)
dotnet test --project tests/MarkView.Avalonia.Tests --filter-class "*.MarkdownViewer*"   # run matching classes
dotnet test --project tests/MarkView.Avalonia.Tests --filter-method "*Avares_source*"    # run matching methods
```

- `dotnet test` runs in Microsoft.Testing.Platform mode with the xUnit v3 runner: filter with `--filter-class` / `--filter-method` / `--filter-namespace` (`*` wildcards at either end). VSTest-style `--filter "FullyQualifiedName~X"` and MSBuild switches such as `-nodeReuse:false` are forwarded to the test host, which then reports "Zero tests ran" (exit code 5) — set `MSBUILDDISABLENODEREUSE=1` in the environment instead.
- Target framework: net10.0, nullable enabled, implicit usings (`Directory.Build.props`).
- Package versions are centrally managed in `Directory.Packages.props` — add new deps there, not inline `Version=` attributes in `.csproj`.
- Test runner: xUnit v3 + `Avalonia.Headless.XUnit`. **Any test that constructs an Avalonia object must use `[AvaloniaFact]`/`[AvaloniaTheory]`**, not `[Fact]`/`[Theory]` — even a bare property set on `TextBlock`/`StackPanel`/`Run` touches `AvaloniaPropertyDictionaryPool` and throws `IndexOutOfRangeException` without platform init. Plain `[Fact]` is only safe when a test constructs zero Avalonia objects (e.g. `SlugGeneratorTests`, `TextMateHighlighterTests`).
- Known upstream flake: `AvaloniaUI/Avalonia#20664` — headless test session cleanup can resume on a different thread, causing sporadic `Dispatcher.VerifyAccess()` failures in `[AvaloniaFact]` tests.
- Coverage via `Microsoft.Testing.Extensions.CodeCoverage` (`testconfig.json`, passed explicitly with `--config-file` in the workflow — routing it through `TestingPlatformCommandLineArguments` in `Directory.Build.props` is NOT honored by this SDK's `dotnet test` MTP mode), measured by the Ubuntu job of `.github/workflows/build.yml`.
- Mutation testing via Stryker (`dotnet-stryker`, pinned in `.config/dotnet-tools.json`, one `stryker-config.json` per test project), reported by `.github/workflows/mutation.yml`. On pull requests it only runs when the PR is labelled `ci-mutation-testing` (adding the label runs it at once for every package, drafts included; later pushes only for the packages the PR touches), with `--since` (only mutants in changed files and those covered by changed tests); pushes to main run it with `--since` the previous main commit (in full if that commit isn't an ancestor, e.g. after a force push), and a manual run of `ci.yml` or the `ci-full` label runs it in full.
- CI (`.github/workflows/ci.yml`): a `changes` job plans the run from the changed paths and labels, and the **Gate** job is the single required check (skipped jobs count as passing). Docs-only PRs run nothing; drafts only build and test on Ubuntu; PRs skip mutation testing unless labelled. Labels: `ci-mutation-testing` (incremental mutation run), `ci-full` (AOT on all OSes and a full mutation run; `pr-labels.yml` runs either as soon as the label is added) and `ci-run-on-draft` (normal suites on a draft, from its next push). Publishing a GitHub release builds the tag and pushes the packages to NuGet.org.
- Test project pattern: inherit `RenderTestBase`, call `Render(markdown)`, and traverse the returned root `StackPanel → children` with `Assert.IsType<T>()` / `.OfType<T>()`. When testing through a full `MarkdownViewer` instead, `viewer.Content` is the rendered `Grid` directly — traverse `Grid → StackPanel → children`; the `ScrollViewer` (`PART_ScrollViewer`) lives in the control's `ControlTemplate`, not in `Content`, and is only reachable via `OnApplyTemplate`/`GetVisualDescendants()` once the control has a template applied (e.g. the `MarkdownTheme.axaml` include). `TestApp.cs` bootstraps `FluentTheme` + `AvaloniaHeadlessPlatformOptions` — copy it when adding a new test project.

## Architecture

Five independently-shipped NuGet packages under `src/`, each with a matching project under `tests/`:

| Package | Role |
|---|---|
| `MarkView.Avalonia` | Core control (`MarkdownViewer`), renderer pipeline, default theme |
| `MarkView.Avalonia.SyntaxHighlighting` | TextMate grammar highlighting; replaces `CodeBlockRenderer` |
| `MarkView.Avalonia.Svg` | SVG image loading; inserted at the front of the image loader chain |
| `MarkView.Avalonia.Mermaid` | Mermaid diagrams rendered to SVG via `Mermaider` (pure .NET, no browser) |
| `MarkView.Avalonia.Math` | LaTeX (`$…$`/`$$…$$`) rendered to bitmaps via `CSharpMath.SkiaSharp`; opt-in (`UseMath()`) since `$` is common in plain prose |

Rendering pipeline (markdown string → control tree):

```
ImageSizePreprocessor  ("![alt](url =WxH)" normalisation)
  → Markdig.Parse(text, pipeline)
  → IMarkViewExtension[].Register(renderer)   ← extension packages plug in here
  → pipeline.Setup(renderer)
  → AvaloniaRenderer.Render(document)
  → Grid.markdown-document { StackPanel (root), DocumentSelectionLayer, LinkFocusLayer }   ← this becomes MarkdownViewer.Content
```

`Content` is hosted by `PART_ScrollViewer`, the named part inside `MarkdownViewer`'s default `ControlTemplate` (shipped in `MarkdownTheme.axaml`); `viewer.Content` itself is the `Grid`, not a `ScrollViewer`.

`RenderMarkdown()` runs `CreateRenderer()` → render → `InstallDocument()`; a streaming session (`BeginStreaming()`) replaces the middle step with `Rendering/LiveDocument.cs`, which re-renders only the open top-level blocks and truncates the renderer and both overlay layers by per-block counts; with `IsIncrementalRenderingEnabled`, a direct `Markdown` set goes through the same `LiveDocument` (`MarkdownViewer.Incremental.cs`), which then also keeps the trailing blocks whose source is unchanged and splices the re-rendered middle into the root panel and both layers (a kept heading whose slug would change, and the footnote group, are rendered again), moving the kept blocks' syntax trees and the renderer's fold states by the edit (`AvaloniaRenderer.ShiftSourcePositions`); unless `BeginStreaming(healIncompleteSyntax: false)`, each update first heals the text (`Rendering/MarkdownHealer.cs` finds the tail block of the current parse, a paragraph or ATX heading, and appends the closers of its open inline syntax to the parse input only, with a second parse only when closers were added); independently of healing, each update sets `AvaloniaRenderer.ProvisionalStart` so `IsProvisional` is true for the block that contains the end of the text and the blocks around it (the final update heals nothing and renders nothing as provisional). A provisional Mermaid or Math block renders as a plain code block (Math delegates to the renderer that would otherwise accept the fenced block).

- `AvaloniaRenderer` (`src/MarkView.Avalonia/Rendering/AvaloniaRenderer.cs`) extends Markdig's `RendererBase` and owns a push/pop stack of `IContainer` — either a `BlockContainer` (wraps a `Panel`) or an `InlineContainer` (wraps an `InlineCollection`). Block renderers call `WriteBlock`, inline renderers call `WriteInline`.
- Block renderers live in `Rendering/Blocks/`, inline renderers in `Rendering/Inlines/`. Registration order in `AvaloniaRenderer.LoadRenderers()` matters when one Markdig type extends another — e.g. `AlertBlockRenderer` must precede `QuoteBlockRenderer` because `AlertBlock` extends `QuoteBlock` and Markdig dispatches to the first renderer whose `Accept()` matches. Extension packages that share a base Markdig type (`MathExtension`/`MermaidExtension`, both fencing off `FencedCodeBlock`) sidestep this by scanning for the first renderer that would already accept their type and inserting just before it, so behavior is independent of `.UseXxx()` call order.
- Extension packages implement `IMarkViewExtension.Register(AvaloniaRenderer)`, with a `viewer.UseXxx()` method and a `MarkdownViewerDefaults.Extensions.AddXxx()` one; [docs/guides/custom-extensions.md](docs/guides/custom-extensions.md) covers the three extension points (renderers, image loaders, code highlighters).
- Lazy rendering (`MarkdownViewer.IsLazyRenderingEnabled`, on by default; `AvaloniaRenderer.IsLazyRenderingEnabled`, off by default): images, formulas, Mermaid diagrams and syntax colours are built via the public `ViewportTracking.RunWhenNearViewport(element, realize)`, which fires once from `EffectiveViewportChanged` when the element is within one viewport height of the visible area, inside the layout pass and before it is drawn. It listens on the element's outermost `ClipToBounds` ancestor below the `ScrollContentPresenter` (Avalonia clips the effective viewport to each clipping ancestor, and a `TextBlock` clips, so an inline image would otherwise see nothing until its paragraph is in view). `Rendering/ScrollAnchor.cs`, run from the viewer's `LayoutUpdated`, shifts the offset when the first top-level block in view (or the target of `ScrollToAnchor`/`FindNext`, until the next scroll) moves; Avalonia's own `IScrollAnchorProvider` anchoring was rejected because it anchors the partly hidden block above. Code blocks hold plain runs until then; images already in `ImageCache` show at once. With it off, image loading is deferred to `AttachedToVisualTree` (to avoid cancelling in-flight loads during layout); the HTTP client is a shared static instance.
- Virtualization (`MarkdownViewer.IsVirtualizationEnabled`, off by default): the renderer's root panel is then a `Rendering/VirtualizingBlockPanel.cs`, whose `Children` still holds every top-level block (so selection entries, link stops, anchors, folding and `LiveDocument` splices see the whole document) while only the blocks within one viewport height of the visible area are its visual and logical children, i.e. styled, laid out and drawn; the rest take their last measured height or an estimate (`Weight`, scaled per block type by the blocks laid out). It re-implements `IChildIndexProvider` so `:nth-child` sees document order. Code that needs a detached block's position calls `Realize` first (find, `ScrollToAnchor`, Tab via `ICustomKeyboardNavigation.GetNext`); code that reads bounds of root children must skip detached ones (`DocumentSelectionLayer.ShownBlocks`, `ScrollAnchor.Choose`), and a theme preset change gives detached blocks their new themes through `ThemeLookup.ReplaceDetached`.
- Theme switching is live: an `IDualThemeCodeHighlighter` (the TextMate one) tokenises each line once with both variants' colours, and a theme switch only recolours the existing runs through shared per-block brushes (`Rendering/Blocks/HighlightedCode.cs`, used by both the TextMate and Mermaid code block renderers). A plain `IThemeAwareCodeHighlighter` gets its runs rebuilt via `HighlightVariant()` instead.
- Cross-block text selection is owned entirely by `DocumentSelectionLayer` (a transparent overlay `Control`), not by individual `TextBlock`s — see [docs/guides/text-selection.md](docs/guides/text-selection.md).
- Find in document (`MarkdownViewer.Find`/`FindNext`/`FindPrevious`) searches the same registered entries in `DocumentSelectionLayer`, which draws the matches under the selection — see [docs/guides/find-in-document.md](docs/guides/find-in-document.md).
- Text direction: `AvaloniaRenderer` sets `FlowDirection` on each block's controls from `Rendering/TextDirection.cs` (first strong letter, HTML `dir`, code always LTR), via its `ObjectWriteBefore`/`ObjectWriteAfter` hooks, so most renderers need no direction code of their own. Avalonia mirrors a right-to-left visual with a render transform, so overlays must map bounds with `VisualBounds.BoundsIn` (`TransformToVisual`), never by adding `Bounds` offsets. Inline code in RTL text is wrapped in a left-to-right isolate (LRI…PDI, `DirectionIsolate`; Avalonia honours isolates from 12.1.4), left out when copying. Avalonia 12.1 mis-hit-tests a right-to-left run that ends a `TextBlock` (`MarkdownSelectableTextBlock.CreateTextLayout` works around it, AvaloniaUI/Avalonia#22530) — see [docs/guides/right-to-left.md](docs/guides/right-to-left.md).
- Links are `Span`s, so they can't take focus or have automation peers. `LinkFocusLayer` (another overlay) hosts one focusable `LinkFocusTarget` per link, kept over the link's text, and `MarkdownViewer` implements `ICustomKeyboardNavigation` to Tab through them in reading order. Each target's Hyperlink peer is reported as a child of its paragraph's peer — see [docs/guides/accessibility.md](docs/guides/accessibility.md).

## Conventions

- CSS-style class names: `markdown-*` (e.g. `markdown-h1`, `markdown-code-block`) — see [docs/reference/style-classes.md](docs/reference/style-classes.md) for the full list.
- Each package that needs overridable colours ships its own `Themes/<Package>Theme.axaml` (`AvaloniaResource` glob in the `.csproj`), included via `StyleInclude` — standalone, does not import `MarkdownTheme.axaml`. Code paths that can't rely on `DynamicResource` (e.g. Mermaid's SVG baked at render time) read the brush via `Application.Current.TryGetResource` and fall back to a hardcoded literal if the theme isn't included. `MarkView.Avalonia.Math` ships no theme file at all — formulas are baked to bitmaps via `CSharpMath.SkiaSharp`, so colours are picked directly from `Application.Current.ActualThemeVariant` and re-baked on theme change.
- Renderers rebuild baked-in colours (Mermaid SVG, Math bitmaps, theme-aware highlighter runs) via the public `ThemeTracking.ReapplyOnThemeChange(element, rebuild)`, which listens to the element's own inherited theme and, while the element is hidden (`IsEffectivelyVisible` false, e.g. a viewer on an inactive tab), waits for the next layout pass that finds it visible. Never subscribe to `Application.Current` events from a renderer — a document that is never shown or is replaced would never unsubscribe, so the application would keep it alive.
- Colours: every literal colour key in `MarkdownTheme.axaml` needs a value in each preset (`GitHubTheme.axaml`, `ChatTheme.axaml`, `DocsTheme.axaml`) as well (`ThemePresetContrastTests` fails otherwise), and the pairs it draws belong in `ThemeContrastTests` / `ThemePresetContrastTests` (4.5:1 text, 3:1 borders that carry meaning, 7:1 for the `MarkdownHighContrast*` palette). High contrast (`MarkdownViewer.HighContrastMode`) is a palette swap, not styles: the viewer merges `MarkdownHighContrastPalette` (in `MarkdownTheme.axaml`) into its own resources while it is on, so a value that changes in high contrast must come from a `DynamicResource` key listed there, and presets only redefine the `MarkdownHighContrast*` keys — see [docs/guides/accessibility.md](docs/guides/accessibility.md#high-contrast). Every style costs a style instance on every control of its selector's type, even one without its class (Avalonia re-checks classes live), plus an expression per `DynamicResource` setter: prefer constants and the narrowest type (e.g. `mrb|HeadingFoldToggle`, not `:is(Control)`), and never add a `:high-contrast` style for a common element.
- Document elements get their look from control themes, not styles: a renderer calls `renderer.ApplyTheme(control, "Markdown<Role>Theme")` (resolved from the viewer by `Rendering/ThemeLookup.cs`, refreshed when the viewer's resources change), and the themes in `MarkdownTheme.axaml` read sizes and spacing from keys that presets redefine (a preset redefines a whole theme only where keys can't express its look). A theme's nested selectors must start at the control itself (`^:nth-child(1)`, `^.class`, `^:expanded`): the XAML compiler silently compiles an ancestor-first one (`Border.x ^`, `:is(mv|MarkdownViewer):high-contrast ^`) as plain `^`. For high contrast use `^[(mv|MarkdownViewer.InHighContrast)=True]`. A renderer test that checks themed values outside a viewer renders with `RenderTestBase.Render(markdown, themed: true)`.
- Renderers that emit non-text controls (images, formulas, diagrams) set the public `MarkdownSelection.CopyText` attached property so selection copies a text equivalent (alt text, `$…$`/`$$…$$` source, fenced Mermaid source). Block controls without it are skipped by selection; see [docs/guides/text-selection.md](docs/guides/text-selection.md).
- File naming: `<Element>Renderer.cs`, `<Feature>Extension.cs`, `<Feature>Highlighter.cs`. Namespaces mirror folder structure.
- Each package that exposes internals to tests grants `InternalsVisibleTo` in its `AssemblyInfo.cs` (core additionally grants `MarkView.Avalonia.Svg`, `MarkView.Avalonia.SyntaxHighlighting` and `MarkView.Avalonia.Mermaid`) — extend those lists rather than making things `public` just to reach them from a test/extension project.
- Shared test helpers (`WaitUntilAsync`, `ThemeScope`, `LoopbackHttpServer`) live in `tests/Shared/` and are compiled into every test project via `tests/Directory.Build.props`.
